## Контекст

Напоминания о корзине надо запускать по времени, а своего планировщика у модуля магазина на сервере нет. На этом же сервере уже есть задача, которую запускает `crontab` хоста.

## Решение

Раз в 30 минут `crontab` хоста запускает задачу напоминаний внутри контейнера API (`docker exec sbonus_api …`), под `flock`. Строку в `crontab` ставит `deploy_shop.sh` и следит, чтобы она не задвоилась.

## Почему

- **cron хоста, как у уже работающей задачи.** На сервере один привычный способ запуска по времени. Задача — отдельный процесс: если она упадёт, API не пострадает. `flock` не даёт двум запускам наложиться друг на друга.
- **Планировщик внутри процесса API.** Отвергнуто: его пришлось бы вводить с нуля. Он жил бы и умирал вместе с API: перезапуск или падение API сбивали бы расписание, а ошибка задачи могла бы задеть приём заказов. А если API когда-нибудь запустят в несколько процессов, каждое напоминание уйдёт по нескольку раз.
- **Отдельный контейнер-планировщик.** Отвергнуто: ещё один сервис в развёртывании ради одной строки расписания.

## Последствия

- Расписание живёт на хосте, вне контейнеров и вне репозитория. После переезда сервера или ручной пересборки его ставит только `deploy_shop.sh`. Если его не запустить, напоминаний не будет, и никто этого не заметит.
- Если перейти на другой планировщик, строку надо убрать со всех хостов. Иначе напоминания уйдут дважды: `flock` защищает только от второго запуска самого cron.
- Задача завязана на имя контейнера `sbonus_api`. Переименуют контейнер — cron молча будет падать каждые 30 минут. Падение задачи не задевает API, но снаружи его и не видно, так что за задачей надо следить отдельно.
- Точность — полчаса: «через 1 день» на деле значит «в течение получаса после суток», а если срок выпал на тихие часы — утром. cron будит задачу круглые сутки, окно 10:00–20:00 по Бишкеку соблюдает сама задача, поэтому часовой пояс сервера нельзя путать с бишкекским.
