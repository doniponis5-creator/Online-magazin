# Спецификация: уведомления на телефон — iPhone в боевом режиме, Android через Firebase

## Задача

Владелец магазина хочет, чтобы покупатель узнавал «Заказ оплачен» и «Заказ готов»
всплывающим сообщением сверху экрана телефона — и на iPhone, и на Android.
Сегодня на iPhone это собрано, но сервер слал в тестовый канал Apple, а приложение
только что вышло в App Store. На Android уведомлений нет совсем: приложению нужен
проект Firebase (служба Google, через которую доставляются уведомления на Android),
а сайт и сервер про Android ничего не знают.

## Решение

- **iPhone** — уже сделано: владелец сам переключил сервер в боевой режим (`APNS_PRODUCTION=1`),
  API поднялся. Здесь остаётся только отметить это в документах проекта.
- **Android** — всё готово «под ключ», кроме двух файлов, которые может получить только
  владелец в своём аккаунте Google:
  1. `google-services.json` — «паспорт» приложения в Firebase, кладётся в Android-проект;
  2. ключ сервисного аккаунта Firebase (JSON) — сервер подписывает им отправку.
  Владелец запускает одну команду `bash scripts/setup-fcm.sh`: она сама находит оба файла
  в «Загрузках», проверяет их, кладёт первый в проект, второй — на сервер (ключ нигде
  не показывается). Дальше — обычное обновление сервера и сайта и новая сборка для Google Play.
- Пока файлов нет, Android-приложение собирается и работает **ровно как сегодня**.

## Решения по реализации

**1. Приложение Android (Capacitor).**
- Плагин `@capacitor/push-notifications` попадает в Android-сборку **только если есть
  `android/app/google-services.json`**: `capacitor.config.ts` решает это при `cap sync`
  проверкой файла. Почему: без Firebase плагин роняет приложение при подписке — так
  записано в конфиге; условие делает «нет файла» ровно сегодняшней сборкой.
- Подключение Google-сервисов в `android/app/build.gradle` по наличию файла уже есть — не трогаем.
- Канал уведомлений «Заказы» (`orders`, высокая важность) создаётся в `MainActivity` при запуске
  (Android 8+). Почему нативно: канал должен существовать до первого уведомления, а не после
  загрузки сайта.
- В манифесте: `POST_NOTIFICATIONS`; метаданные Firebase — значок по умолчанию (новый
  монохромный векторный силуэт «S», белый на прозрачном), цвет `@color/brand_lemon`,
  канал по умолчанию `orders`.
- `PushNotifications.presentationOptions = ["alert", "sound"]` — уведомление видно и при
  открытом приложении (плагин читает это на Android). Новую сборку для iPhone в этом заходе
  **не делаем**: приложение 1.0 только что вышло в App Store, на iPhone поведение не меняется,
  настройка просто окажется в следующей сборке, когда её решит владелец.
- `versionCode` 3 → 4, `versionName` не меняем без нужды (решит сборка).
- `google-services.json` **коммитится в репозиторий**. Почему: без него сборка на другом
  компьютере (ПК владельца) молча выйдет без уведомлений; ключ внутри — публичный ключ
  клиента, он и так лежит в каждой скачанной APK.

**2. Сайт.**
- `src/lib/native/push.ts` сообщает платформу по `Capacitor.getPlatform()` (`ios` / `android`),
  а не жёсткое `'ios'`.
- `POST /api/push/device` принимает `{token, platform}`: `ios` — шестнадцатеричная строка
  60–200 знаков (как сейчас); `android` — адрес FCM: буквы, цифры, `_ - :`, 100–1024 знака.
  Неизвестная платформа → 400. Отсутствие `platform` = `ios` (старые установки iPhone).
- `registerPushDevice(token, phone, platform)` передаёт платформу серверу.
- «Кабинет»: текст при запрете уведомлений зависит от платформы — новый ключ словаря
  `pushDeniedAndroid` (ru + ky), iPhone-текст не меняется.

**3. Сервер SBonus (модуль `shop`).**
- Отправка разделяется по платформе: Apple (как сейчас) и FCM HTTP v1 (новое). `send()`
  читает пары (адрес, платформа) и шлёт каждому своим путём; итог — сколько доставлено.
- FCM: ключ сервисного аккаунта хранится одной строкой base64 в `/opt/sbonus/.env.production`
  как `FCM_SERVICE_ACCOUNT_B64`. Из него: `project_id`, `client_email`, `private_key`.
  Сервер подписывает JWT RS256 (библиотека `cryptography`, уже стоит), меняет его на токен
  доступа Google (`oauth2.googleapis.com/token`, область `firebase.messaging`), держит ~50 мин.
  Сообщение: `notification{title, body}`, `data` (только строки), `android{priority: HIGH,
  notification{channel_id: "orders", sound: "default"}}`.
- Чистая логика FCM (сборка сообщения, подпись, разбор ответа) — отдельный модуль без
  импортов приложения, чтобы его можно было проверить тестами на Mac.
- Приём адреса (`/webhook/site/push-device`): платформа из `{ios, android}`, иначе отказ;
  длина до 200 для `ios`, до 1024 для `android`.
- Миграция `009`: `shop_push_devices.token` → `VARCHAR(1024)`. Только расширение, данные не трогаются.
  `deploy_shop.sh` знает о `009`.
- Нет ключа FCM → Android молчит, iPhone работает. Ключ неверный / Google недоступен → запись
  в журнал без адресов целиком и без ключа, заказ не страдает.

**4. Владельцу.**
- `scripts/setup-fcm.sh` (Mac) и `scripts/setup-fcm.ps1` (Windows) + серверная часть
  `scripts/fcm-remote.sh` — по образцу `setup-apns.*` / `apns-remote.sh`: ищут
  `google-services.json` и `*firebase-adminsdk*.json` в «Загрузках», проверяют, копируют
  первый в `android/app/`, второй передают на сервер через stdin (не в аргументах),
  сервер проверяет и пишет в `.env.production` с резервной копией. Ответы: `FCMOK`, `BADJSON`,
  `NOTSA`, `NOENV`.
- `docs/ANDROID_PUSH_UZ.md` — пошагово (узбекская латиница, как соседний `ANDROID_PLAY_UZ.md`):
  Firebase → добавить Android-приложение `kg.smarket.app` → скачать `google-services.json` →
  «Сервисные аккаунты» → «Создать закрытый ключ» → `bash scripts/setup-fcm.sh`. Дальше — готовые
  команды, дословно:
  1. сервер: `ssh root@145.223.100.16 "rm -rf /tmp/sb_shop"`, затем
     `scp -r integrations/sbonus-server/shop root@145.223.100.16:/tmp/sb_shop`, затем
     `ssh root@145.223.100.16 "bash /tmp/sb_shop/deploy_shop.sh"` (он же пересоздаёт API — ключ FCM подхватится);
  2. сайт: `bash scripts/update-all.sh --only-site`;
  3. Android: команда сборки и копирования `.aab` из раздела 5 `docs/ANDROID_PLAY_UZ.md`
     (versionCode уже 4) → файл `build-play/smarket-1.0-code4.aab` → загрузка в Google Play
     по разделу 3 той же инструкции.
  Собрать `.aab` на этом Mac может и агент (ключ подписи здесь) — это локальное действие;
  обновить сервер/сайт и загрузить в Google Play — внешние действия, их делает владелец
  или агент по его отдельному «да».
- Владелец дал разрешение на iPhone и спросил, как это работает (Дополнения): в чате дан ответ
  и команда пробного уведомления на его iPhone — вне кода.

**5. Как ведётся работа.** Ветка `claude/push-apns-fcm` от свежего `feature/ios-app`
(перенос рабочей копии одобрен владельцем). В конце: проход `/impeccable` по видимому —
значок и вид уведомления на Android, текст «Кабинета» при запрете — и обновление карты
проекта `graphify update`, как принято в репозитории («chore: карта проекта»).
- `docs/TODO_NEXT.md`, `docs/IOS_APP_UZ.md`, `docs/APP_STORE_UZ.md`: пункт «переключить push в
  боевой режим» закрыт 27.09.2026 владельцем.

**6. Напоминание о корзине (G01, добавлено владельцем по ходу).**

Сегодня корзина живёт только на телефоне (`localStorage`), сервер о ней не знает — поэтому
сначала корзина должна доехать до сервера.

- **Кому:** только в приложении (iPhone/Android), только вошедшему покупателю, только если он
  **сам согласился** (правило Apple 4.5.4: напоминания — это маркетинг, нужно явное согласие в
  интерфейсе и способ отказаться). Согласие — карточка в «Кабинете»: «Напоминать о товарах в
  корзине?» — «Да, напоминать» / «Нет». После ответа — переключатель там же. Карточка видна,
  только когда уведомления разрешены. Сайт в браузере ничего не шлёт.
- **Что уходит на сервер:** снимок корзины вошедшего покупателя — названия (первые 3), число
  позиций, сумма. Отправляется при каждом изменении корзины в приложении (с задержкой ~5 с, чтобы
  не слать на каждое нажатие) и при входе. Пустая корзина — тоже снимок (0 позиций). Без
  входа — ничего.
- **Хранение:** таблица `shop_cart_reminders` (миграция `010`): номер телефона (ключ), согласие,
  состав (JSON), число позиций, сумма, когда корзина менялась, сколько напоминаний отправлено,
  когда последнее. Любое изменение корзины сбрасывает счётчик.
- **Когда:** расписание — **ждёт ответа владельца** (предложено: через 1 день, ещё через 3, ещё через
  7 — и тишина; альтернатива — каждые 3 дня до покупки). Только с 10:00 до 20:00 по Бишкеку.
  Не шлём, если: нет согласия, корзина пуста, нет адреса телефона для уведомлений, после изменения
  корзины был оформлен заказ этим номером.
- **Текст:** заголовок «Товары ждут в корзине», тело «{первый товар}{ и ещё N} — оформите заказ,
  когда будет удобно.» Без выдуманной срочности («осталось 2 штуки» — нельзя). `data: {type: "cart"}`.
- **Нажатие:** уведомление с `type: "cart"` открывает корзину; остальные — как сейчас. Делается в
  JS сайта (слушатель нажатия плагина) — работает и в вышедшем iPhone-приложении без новой сборки.
- **Запуск по времени:** у модуля магазина своего планировщика нет. Как у существующей задачи на
  сервере — строка `crontab` хоста раз в 30 минут: `docker exec sbonus_api python3 -m app.shop.shop_cart_remind`
  под `flock`. `deploy_shop.sh` ставит строку сам и не дублирует. Падение задачи не задевает API.
- **Удаление учётной записи** стирает и строку напоминаний этого номера.

## Границы и швы

| Модуль | Владеет | Выставляет | Прячет |
|---|---|---|---|
| сайт `native/push` | разрешение и адрес телефона в приложении | `enablePush(): Promise<boolean>`, `pushState(): Promise<'granted'\|'denied'\|'ask'\|'none'>`, `resumePush(): Promise<void>`, `pushPlatform(): 'ios'\|'android'\|null` | как найти плагин, куда отправить адрес |
| сайт `POST /api/push/device` | приём адреса от приложения | тело `{token: string, platform?: 'ios'\|'android'}` → `200 {ok:true}` / `400 {ok:false, error:'token'\|'platform'}` | проверку формы адреса по платформе |
| сайт `customer/gateway` | разговор с SBonus | `registerPushDevice(token, phone, platform)` → серверу `{token, platform, phone}` | подпись запроса, тестовый режим |
| сервер `shop_push` | отправку на телефоны | `send(db, phone, title, body, data) -> int`, `save_device(db, token, platform, phone)`, `forget_phone(db, phone) -> int` — **сигнатуры не меняются** | выбор Apple/FCM по платформе, чистку мёртвых адресов |
| сервер `shop_push_fcm` (новый, без импортов приложения) | протокол FCM | `load_account(b64) -> dict\|None`, `build_assertion(account, now) -> str`, `build_message(token, title, body, data) -> dict`, `classify(status, body) -> 'ok'\|'drop'\|'fail'\|'auth'` | формат JWT и ответов Google |
| сервер `/webhook/site/push-device` | приём адреса от сайта | `{token, platform, phone}` | лимиты по платформе |
| приложение Android | канал, значок, разрешение | канал `orders`; плагин есть ⇔ есть `google-services.json` | — |

**Швы для тестов:** сайт — `POST /api/push/device` (vitest, как остальные маршруты) и
`pushPlatform()`; сервер — `shop_push_fcm` (unittest, запуск на Mac через `uv run --with cryptography`).
Сборка Android — две сборки `assembleDebug`: без файла и с учебным (поддельным) `google-services.json`
во временной копии, который не коммитится.
